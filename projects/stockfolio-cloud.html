01OVERVIEW

미디어를 저장하는 것을 넘어, 관리하는 경험까지

사용자가 파일 전송 상태를 파악하고, 업로드한 콘텐츠를 필요한 순간 다시 찾을 수 있도록 화면과 상태 흐름을 구성했습니다.

프로젝트에서 맡은 일

클라우드의 파일 목록·상세 화면, 멀티파트 업로드 인터랙션, 폴더 이동·공유·다운로드 작업, 프로필 및 인증 관련 화면을 프론트엔드에서 구현했습니다. 각 기능은 API 모듈과 MobX Store, 재사용 가능한 UI 컴포넌트로 연결했습니다.

02CORE IMPLEMENTATION

분할 업로드를 하나의 경험으로 연결하다

대용량 파일은 전송 과정이 여러 요청으로 나뉩니다. 사용자는 그 복잡한 과정 대신 현재 진행 상태와 취소 여부를 알 수 있어야 합니다.

PROBLEM

하나의 파일, 여러 번의 네트워크 요청

업로드 시작 요청, 파일 조각 전송, 완료 요청이 분리되어 있습니다. 이를 사용자 관점에서는 하나의 작업으로 표시해야 했습니다.

APPROACH

전송 단계를 나누고 상태는 모으기

서버에서 수신한 업로드 URL과 조각 크기를 사용해 파일을 분할하고, 조각별 진행률을 파일 단위 진행 상태로 합산했습니다.

  1. 01

    전송 시작

    파일명·MIME 타입·크기를 전달해 업로드 정보를 요청

    startUpload
  2. 02

    파일 분할

    서버가 제공한 조각별 크기로 Blob을 분할

    File.slice
  3. 03

    병렬 전송

    각 업로드 URL에 파일 조각을 전송하고 ETag 수집

    Promise.all + Axios
  4. 04

    전송 완료

    파일 ID와 ETag 목록을 전달해 업로드 완료 요청

    finishUpload
FILE TRANSFER / KEY LOGICTypeScript
// 실제 구현의 핵심 흐름을 축약한 예시
const chunk = file.slice(
  pointer,
  pointer + upload.contentLength
);

const result = await sendFile(
  upload,
  file.type,
  chunk,
  onProgress,
  cancelToken
);

// 조각별 ETag를 수집한 뒤 완료 요청
await finishUpload(stockFileId, etags);

업로드 요청 → 전송 → 완료를 독립된 API로 분리했습니다.

↗

진행률 집계

각 조각의 전송 진행률을 집계하고, 업로드 중인 파일별 상태를 화면에 표시했습니다.

×

전송 취소

Axios CancelToken으로 진행 중인 조각 요청을 취소하고 모달 상태를 정리했습니다.

✓

완료 확인

서버가 요구하는 ETag 목록을 모은 뒤 파일별 완료 API를 호출했습니다.

* 확인된 소스 기준: 병렬 업로드, 진행률 표시, 취소 기능은 구현되어 있으며 자동 재시도 및 중단 지점 업로드 재개 기능은 확인되지 않았습니다.

03USER EXPERIENCE

업로드한 파일을 찾고, 선택하고, 활용하는 흐름

클라우드의 핵심은 업로드 이후에도 이어집니다. 파일 탐색부터 일괄 관리, 미디어 상세보기와 공유까지 사용 흐름을 연결했습니다.

01

파일·폴더 탐색

디렉터리 데이터를 바탕으로 폴더 경로를 이동하고, 파일을 썸네일형 또는 목록형으로 표시했습니다.

DirectoryGrid / ListSorting
02

다중 선택과 일괄 작업

선택한 파일들을 MobX Store에서 관리하고, 이동·삭제 작업 및 결과에 따른 목록 갱신을 연결했습니다.

SelectionBatch ActionMobX
03

미디어 상세보기

이미지·동영상을 구분해 뷰어를 표시하고, 파일 정보와 다운로드·공유·이름 변경 기능을 제공했습니다.

Media ViewerMetadataShare
04

사용자·공통 인터랙션

프로필 정보, 저장 용량, 인증 상태, 다단계 확인 모달을 각각의 역할에 맞는 Store와 UI로 구성했습니다.

ProfileStorageModal
DESKTOP & MOBILE

같은 데이터를, 화면 환경에 맞는 상호작용으로

데스크톱은 사이드 탐색·목록 전환·업로드 작업에 집중하고, 모바일은 독립된 파일 상세 화면과 간결한 탐색 UI를 사용합니다. 모바일 업로드는 지원 기능으로 단정하지 않고, 소스에서 확인된 PC 업로드 안내 동작을 기준으로 설명합니다.

04ARCHITECTURE

화면의 복잡도를 역할별 계층으로 분리하다

MobX는 공통 상태와 페이지별 상태를 구분하고, UI는 재사용 단위에 따라 구성했습니다. API 요청과 데이터 모델도 별도 모듈로 관리했습니다.

설계 포인트

API의 성공·실패 응답 타입을 구분하고, FileDataModel과 UploadResModel 등 TypeScript 모델을 공통 사용하여 상태·화면·서버 응답의 연결 기준을 마련했습니다.

05REVIEW & NEXT STEPS

구현 경험을 다음 설계의 기준으로

아래 항목은 개발이 완료된 개선 성과가 아니라, 현재 소스를 다시 검토하며 도출한 리팩터링 과제입니다.

IMPROVEMENT 01

부분 실패 응답의 정교한 처리

파일 이동·삭제 시 일부 요청만 성공할 수 있으므로, 작업별 성공·실패 상태를 사용자에게 개별적으로 전달하도록 개선할 수 있습니다.

IMPROVEMENT 02

비동기 작업과 리소스 정리

모달 이벤트 리스너와 Lottie 인스턴스의 정리 흐름을 보완하고, 업로드 오류·취소 이후의 정리 동작을 강화할 수 있습니다.

IMPROVEMENT 03

타입 안정성과 책임 분리

Storybook 파일에 포함된 실제 서비스 로직을 분리하고, 외부 SDK의 any 타입 및 API 응답 모델을 더 구체화할 수 있습니다.
